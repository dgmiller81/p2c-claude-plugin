# p2c — Gated Review & Requirements Traceability

**Date:** 2026-08-11
**Status:** Approved for planning
**Repo:** `dgmiller81/p2c-claude-plugin`
**Branch:** `feature/gated-review-traceability`

## Problem

p2c today has roles but no protocol. Its five relevant agents (`product-owner`,
`business-analyst`, `lead-architect`, `lead-ux-designer`, `lead-developer`)
each produce artifacts, but nothing forces them to review each other's work,
nothing proves a requirement survived the trip from PRD to mockup, and nothing
detects that a mockup went stale when its requirement changed.

The existing controls are assertions, not mechanisms:

- `visual-standards.md` declares mockups mandatory and enterprise-grade — but a
  human has to eyeball whether that's true.
- `business-analyst.md` describes a requirements traceability matrix — but it is
  a suggested table format, generated by hand, verified by nobody.
- `status.json` tracks phase completion — but a phase can be marked `delivered`
  with orphaned requirements and broken mockup links.

The result is the failure this spec exists to prevent: **requirements quietly
disappear between stages, and nobody notices until build.**

Two secondary problems, surfaced during design:

- p2c has no persona artifact and no journey-map artifact at all, despite both
  being central to the handoff the user needs.
- p2c ships zero mockup templates, so every run redraws the component language
  from scratch and consistency is luck.

## Goals

1. Every requirement is provably represented in the design before engineering
   sees it, or is explicitly and traceably dropped.
2. Product/BA, UX, Architecture, and Development review each other's work at
   defined gates, producing structured, actionable findings.
3. HTML mockups form a 100% complete, fully linked, clickable walkthrough —
   machine-verified, not asserted.
4. Personas, journey maps, and screens each carry a plain `.md` sidecar that a
   downstream agent can consume without parsing HTML.
5. When anything upstream changes, every affected downstream artifact is
   flagged automatically and its sign-off is voided.
6. Implementation is held by default. The pipeline delivers requirements and
   design; code starts only on explicit opt-in.

## Non-goals

- Replacing p2c's phase model. This is a cross-cutting protocol invoked by
  phases 2, 3, and 4; phase numbering and existing commands are preserved.
- Agent-to-agent negotiation. Disagreements escalate to the human; they are not
  resolved by further agent rounds.
- Fetching external URLs during link checking (opt-in via `--check-external`).
- Replacing ProdReq. ProdReq becomes archive; its assets are ported here.

## Decisions taken

| Decision | Choice | Rationale |
|---|---|---|
| Host | p2c plugin; port ProdReq assets in | p2c is git-backed, installed, and has the role roster the review loop needs |
| Traceability storage | Sidecar frontmatter + generated index | Parallel-agent safe; verification is one command with an exit code |
| Review loop bound | Max 2 rounds, then escalate to user | Bounded cost; convergence guaranteed by the anti-thrash rule |
| Change propagation | Flag downstream STALE; owning agent repairs | No silent overwrite of reviewed and signed work |
| Trace chain | Typed per requirement kind and surface | Avoids forcing artificial screens onto headless requirements |
| Sign-off points | Three human gates | Meaningful oversight without approval fatigue |
| Build posture | Held by default, explicit opt-in | Prevents coding against an incomplete design |

## Architecture

### The handoff protocol

A single protocol instantiated three times with different reviewer sets. Phases
2, 3, and 4 invoke it rather than each implementing bespoke review logic.

```
STAGE R — REQUIREMENTS
  author    product-owner + business-analyst
            → prd.md, brd.md, register/ (FR/NFR/BR with stable IDs)
  review ⇉  lead-ux-designer ∥ lead-architect
  fix       product-owner + business-analyst resolve
  ══ GATE 1 · REQUIREMENTS BASELINED · human sign-off ══
            requirement IDs freeze; later changes are versioned

STAGE D — DESIGN
  author    lead-ux-designer
            → personas, journeys, screens, HTML mockups + states, sidecars
  review ⇉  product-owner ∥ business-analyst ∥ lead-architect
  round 2   UX updates → same reviewers re-run → remainder escalates
  ══ GATE 2 · UX APPROVED · human sign-off + trace.py + linkcheck.py ══

STAGE E — ENGINEERING HANDOFF
  review ⇉  lead-architect ∥ lead-developer
            input: the UX package *plus* the traceability matrix
  ══ GATE 3 · HANDOFF ACCEPTED · human sign-off ══
            work breakdown proceeds; build remains held unless opted in
```

Invariants:

- **Reviewers never review their own output.** UX reviews requirements; UX does
  not review its own designs.
- **Reviews fan out in parallel.** Reviewers are independent; sequential
  dispatch would multiply wall-clock for no gain.
- **Gates are machine-blocked as well as human-blocked.** Human sign-off is
  necessary but not sufficient at Gate 2.

### ID scheme

| Prefix | Artifact | Example |
|---|---|---|
| `BR-###` | Business requirement | `BR-005` |
| `FR-###` | Functional requirement | `FR-012` |
| `NFR-###` | Non-functional requirement | `NFR-003` |
| `P-##` | Persona | `P-02` |
| `J-##` / `J-##.#` | Journey map / step | `J-01.4` |
| `SCR-###` | Screen | `SCR-004` |
| `ARC-###` | Architecture component | `ARC-002` |
| `US-###` | Story | `US-031` |
| `TC-###` | Test case | `TC-004` |
| `F-<gate>-r<n>-###` | Review finding | `F-g2-r1-007` |

IDs are assigned at Gate 1 for requirements and at authoring time for
everything else. They are never reused and never renumbered.

### Sidecar schema

Common frontmatter on every sidecar:

```yaml
id:           <ID>
type:         requirement | persona | journey | screen | component | story | test
title:        <string>
traces_to:    [<upstream IDs>]
status:       draft | in-review | approved | stale
source_hash:  {<upstream ID>: <hex>}
signoff:      {by: <who>, date: <YYYY-MM-DD>, gate: <gate id>}
```

A requirement adds `kind` (`functional` | `non-functional` | `business`),
`surface` (`ui` | `system`), `statement`, `acceptance_criteria`, `source`,
`priority`, `version`, and `changelog`.

A screen adds `personas`, `journey_steps`, `mockup`, `states` (a map of state
name to file), and `terminal`.

A journey adds `persona` and `steps` (ordered list, each with `id`, `label`,
and `screen`).

Example requirement:

```yaml
---
id: FR-012
type: requirement
kind: functional
surface: ui
title: Dispatcher resolves a shipment exception
statement: >
  A dispatcher can view unresolved shipment exceptions, assign one to
  themselves, and record a resolution reason.
acceptance_criteria:
  - Given an unresolved exception, when the dispatcher assigns it, then it
    leaves the unassigned queue within 2s.
  - Resolution requires a reason from the controlled list.
source: {type: stakeholder, ref: Ops lead interview 2026-08-04}
priority: must
version: 1
status: baselined
---
```

Example screen sidecar:

```yaml
---
id: SCR-004
type: screen
title: Shipment Exceptions Queue
traces_to: [FR-012, FR-014, NFR-003]
personas: [P-02]
journey_steps: [J-01.4, J-01.5]
mockup: SCR-004.html
states:
  default: SCR-004.html
  empty:   SCR-004-empty.html
  error:   SCR-004-error.html
terminal: false
source_hash: {FR-012: a3f9c1, FR-014: 77b204, NFR-003: e1d880}
status: approved
signoff: {by: user, date: 2026-08-11, gate: gate2}
---
```

Below the frontmatter, prose a downstream agent can act on: what the screen
does, its primary action, edge cases, open questions. This is the agent-facing
contract — a developer agent reads `SCR-004.md` and never parses HTML.

### Hashing

`source_hash` records, per upstream ID, the SHA-256 (first 6 hex chars) of that
upstream artifact's **normative fields only**:

- Requirement: `statement` + `acceptance_criteria`, YAML-normalized
  (whitespace collapsed, list order preserved).
- Persona / journey / screen: `title` + body prose below the frontmatter.

Editing a note, a source citation, or a priority does not invalidate downstream
work. Editing what the requirement actually demands does.

### Trace chain rules

`trace.py` enforces a different required chain per requirement kind and surface:

| Requirement | Full chain | Failure conditions |
|---|---|---|
| `functional` + `surface: ui` | req → persona → journey step → screen → mockup with all declared states → ARC → US | no screen traces to it; screen has no persona; journey step has no screen; a declared state file is missing |
| `functional` + `surface: system` | req → ARC → TC → US | no component owns it; no test asserts it |
| `non-functional` | req → ARC → TC → US | no component owns it; no test asserts it |
| `business` | decomposes into ≥1 FR or NFR, which follow their own chains | terminal BR with no children |

### Staged enforcement

The full chain is only satisfiable at the end. Architecture components do not
exist at Gate 2, and stories do not exist until after Gate 3 — so demanding the
complete chain at every gate would make every gate unopenable.

`trace.py --stage <stage>` enforces progressively, each stage a superset of the
one before:

| Stage | Gate | Additionally enforces |
|---|---|---|
| `requirements` | 1 | schema valid; IDs unique and well-formed; no dangling `traces_to`; every BR decomposes into ≥1 FR or NFR |
| `design` | 2 | every `surface: ui` requirement reaches persona → journey step → screen; every declared state file exists; every screen traces to ≥1 requirement; no orphan personas or journeys |
| `handoff` | 3 | every requirement reaches an ARC component; every `system`/`non-functional` requirement reaches a TC |
| `build` | post-Gate-3, build only | every requirement reaches a US |

Staleness detection and sign-off voiding run at every stage. A bare `trace.py`
with no `--stage` defaults to the highest stage whose gate has been signed, so
the orchestrator cannot accidentally under-check.

All links are bidirectional in `index.json`, so `gaps.md` reports both
directions:

- **Orphan requirement** — a requirement nothing traces to. The lost-requirement
  case.
- **Orphan artifact** — a screen or component tracing to nothing. The
  scope-creep case: work nobody asked for.

## Components

### `trace.py`

Walks `p2c-workspace/`, parses every sidecar, and emits three files.

Responsibilities:

1. **Schema validation** — every sidecar has required fields with valid values;
   every ID matches its prefix pattern; no duplicate IDs; every `traces_to`
   target exists.
2. **Graph construction** — bidirectional edges from `traces_to`, `personas`,
   `journey_steps`, and `states`.
3. **Chain enforcement** — per the table above, by requirement kind and surface.
4. **Staleness detection** — recompute normative hashes, compare to
   `source_hash`, mark mismatches stale and cascade transitively downstream.
5. **Sign-off voiding** — any artifact transitioning to `stale` has its
   `signoff` cleared and recorded in `gaps.md`.

Outputs:

- `traceability/rtm.md` — human-readable matrix, one row per requirement, with
  its full chain and status.
- `traceability/index.json` — the graph, for other tools and agents.
- `traceability/gaps.md` — orphan requirements, orphan artifacts, broken
  chains, and a Staleness section listing what changed, what is affected, and
  which agent owns each repair.

Exit codes: `0` clean; `1` gaps found; `2` schema or parse error.

Staleness repair ownership: UX owns personas, journeys, screens; architect owns
components; scrum-master owns stories; BA owns the register.

### `linkcheck.py`

Validates that the mockup set is a complete, navigable walkthrough. Seven
checks:

1. **Link resolution.** Every `href` and `src` resolves — relative paths exist
   on disk, `#anchor` targets exist in the destination document. Dead stubs
   (`href="#"`, `href=""`, `javascript:void(0)`) are failures.
2. **Reachability.** Every screen is reachable from `index.html` by graph
   traversal. Unreachable pages are reported as orphans.
3. **No dead ends.** Every page has an outbound link. Exempt only if its
   sidecar declares `terminal: true`, making every dead end deliberate.
4. **Nav shell.** Prev / next / index footer present and correct on every
   mockup (ported from ProdReq's clickable-prototype pattern).
5. **State completeness.** Every state declared in a sidecar's `states` map
   resolves to a real file or a real in-page anchor. Declaring a state that was
   not built is a failure.
6. **Golden path walkability.** For each journey map, the declared step
   sequence is provably clickable from step 1 to step N without leaving the
   mockup set.
7. **Placeholder scan.** Fails on `Lorem ipsum`, `TODO`, `Item 1`, `John Doe`,
   `Jane Smith`, `Acme Corp`, `$1,234.56` — the disqualifier list already
   written into `visual-standards.md`, now enforced.

Also **generates `index.html`**: the mockup hub listing every screen, its
states, its trace IDs, and its reachability status.

Outputs `03-design/mockups/linkcheck-report.md` — a per-screen pass/fail table
plus the reachability graph, so a failure names the exact page and link.

Exit codes: `0` clean; `1` checks failed; `2` parse error.

External URLs are recorded but not fetched unless `--check-external` is passed.

### Review protocol

Each reviewer writes one file per gate-round at
`reviews/<gate>-round<n>/<agent>.md`:

```yaml
---
gate: gate2
round: 1
reviewer: lead-architect
verdict: changes-requested        # approved | changes-requested
findings:
  - id: F-g2-r1-007
    severity: blocking            # blocking | should-fix | note
    category: missing-trace       # missing-trace | state-gap | infeasible
                                  # ambiguous | inconsistent | scope-creep
    target: SCR-004
    refs: [FR-014]
    summary: >
      FR-014 (bulk reassign) has no control anywhere in the mockup set.
    proposed_fix: >
      Add bulk-select + reassign to SCR-004, or split into a new screen.
---
```

**A finding without `target` or `refs` is rejected as unactionable.** This is
what keeps reviews from degenerating into unfalsifiable commentary.

**Merge.** The orchestrator collects all reviewer files, dedupes on
`(target, refs, category)`, and writes `merged.md` as one ranked list. Findings
where reviewers contradict each other are marked `conflict: true` and routed
directly to the human.

**Rounds.**

- Round 1: reviewers run in parallel → merged findings → the owning agent fixes
  every `blocking` finding and either addresses each `should-fix` or records why
  not.
- Round 2: the same reviewers re-run with round-1 findings and a diff of what
  changed. Each prior finding is marked `resolved` or `unresolved`.
- Hard stop after round 2. Anything still `blocking` or `unresolved` escalates.

**The anti-thrash rule.** In round 2 a reviewer may not raise a *new* blocking
finding against an artifact unchanged since round 1. If they saw it and passed
it, it is not blocking now. New findings against *changed* artifacts are
permitted, since a change may have broken something. Without this rule two
rounds does not converge — it truncates mid-argument and dumps a full inbox on
the human.

**Escalation.** `reviews/<gate>-escalation.md`, presented in chat as a numbered
decision list. Each item states what is wrong, who raised it, why round 2 did
not close it, and 2–3 options with a recommendation. Each human ruling closes
the finding as `fixed`, `accepted-risk`, or `deferred` and lands in
`config.json` `decisions_log` with a date.

### Gate conditions

| Gate | Opens when |
|---|---|
| **1 — Requirements baselined** | all reviewer verdicts `approved` or all open findings ruled; `trace.py --stage requirements` exit 0; human sign-off |
| **2 — UX approved** | all reviewer verdicts `approved` or all open findings ruled; `trace.py --stage design` exit 0; `linkcheck.py` exit 0; human sign-off |
| **3 — Handoff accepted** | architect and developer verdicts `approved` or ruled; `trace.py --stage handoff` exit 0; human sign-off |

Gate state lives in `config.json`:

```json
{
  "build_enabled": false,
  "gates": {
    "gate1": {"status": "signed", "date": "2026-08-11", "by": "user"},
    "gate2": {"status": "open", "round": 2},
    "gate3": {"status": "pending"}
  },
  "decisions_log": []
}
```

### Build hold

Default `build_enabled: false`. The pipeline runs R → D → E and stops with a
signed handoff package. No code is written.

Unlocked by explicit opt-in only:

| Trigger | Effect |
|---|---|
| `/p2c:full --build`, or `/p2c:tech-build` / `/p2c:poc` / `/p2c:tech-prod` | explicit command opt-in |
| User says "start building" after Gate 3 | conversational opt-in, recorded in `decisions_log` |

**Precondition, enforced on both paths:** Gates 1, 2, and 3 signed, and both
checkers green. If a build command is invoked earlier, the orchestrator refuses,
reports which gate is open, and offers to run the missing stage instead.

This inverts p2c's current behavior, where `/p2c:tech-build` proceeds against an
incomplete phase 3.

## Testing

The checkers are load-bearing — a false green defeats the entire design — so
they are built test-first against fixture workspaces under
`tests/fixtures/`.

| Fixture | Asserts |
|---|---|
| `clean/` | both checkers exit 0 |
| `orphan-requirement/` | `trace.py` exit 1, names the requirement |
| `orphan-screen/` | `trace.py` exit 1, flags scope creep |
| `broken-chain/` | journey step with no screen → exit 1 |
| `stale-hash/` | requirement edited after sign-off → stale cascade, signoff voided |
| `dead-link/` | `linkcheck.py` exit 1, names page and href |
| `unreachable-page/` | reachability failure |
| `undeclared-state/` | sidecar declares `error`, file absent → exit 1 |
| `dead-end/` | non-terminal page with no outbound link → exit 1 |
| `placeholder-content/` | `Lorem ipsum` present → exit 1 |
| `nfr-chain/` | NFR with ARC + TC passes without a screen |
| `bad-schema/` | missing required field → exit 2 |

Protocol behavior — anti-thrash enforcement, merge dedup, escalation
formatting — is verified by a fixture review set with known-duplicate and
known-conflicting findings.

## Implementation sequencing

This is too large for one plan. It decomposes into three increments, each
independently valuable and independently testable. Build in order — each
depends on the one before.

**Increment 1 — Traceability core.** Sidecar schemas, ID scheme, templates for
requirement/persona/journey/screen/component, `trace.py` with staged
enforcement, and its fixtures. Deliverable: you can author artifacts by hand and
`trace.py` correctly reports gaps and staleness. No agent or command changes
yet.

**Increment 2 — Mockup completeness.** `linkcheck.py` and its fixtures, the
ProdReq template port (`persona-card.html`, `journey-map.html`, `_brand.css`,
14 mockup variants), `index.html` generation, and the `visual-standards.md`
reconciliation. Deliverable: a mockup set can be proven complete and walkable.

**Increment 3 — Protocol wiring.** `handoff-protocol.md`, the reviewer-protocol
sections across all five agents, gate wiring in the commands, build hold, the
new `/p2c:review` and `/p2c:trace` commands, `SKILL.md` updates, and the visual
server routes. Deliverable: the full gated pipeline runs end to end.

Increments 1 and 2 are pure tooling with no behavioral risk to existing p2c
runs. Increment 3 is where existing command behavior changes, so it lands last
and gets an end-to-end trial run on a throwaway product idea before use.

## Risks

| Risk | Mitigation |
|---|---|
| Agents write malformed frontmatter | `trace.py` validates schema and fails loudly with the offending file and field; templates give a correct starting point |
| Two rounds insufficient for genuinely contested design | Escalation list is explicitly designed for this; the human rules and the decision is recorded |
| Hash churn from cosmetic requirement edits | Hash covers normative fields only |
| Checkers become a bottleneck on large workspaces | Both are single-pass file walks; `index.json` is cached and only rebuilt on mtime change |
| Ported ProdReq templates drift from p2c's Enterprise Default Style | Port includes a reconciliation pass aligning `_brand.css` tokens with `visual-standards.md` |

None. All design decisions are resolved above.
